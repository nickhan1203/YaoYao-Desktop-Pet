# CodeBuddy AI 开发工作流

## 1. 每次任务的闭环
1. 确认 CodeBuddy 已加载 `CODEBUDDY.md` 与项目规则；规则变更后新建对话验证。
2. 让 CodeBuddy 阅读相关文档与现有实现，先复述目标、非目标、修改范围和风险。
3. 将任务拆成最小可验收单元。
4. 让 CodeBuddy 实现最小改动。
5. 查看 diff，重点检查 Electron 安全设置、资源路径、生命周期与 IPC。
6. 运行真实存在的测试、类型检查、构建命令。
7. 在 Mac 验证 macOS 行为；将对应 Windows 检查列入待测清单。
8. 提交 Git，Windows 拉取同一 commit SHA 并完成 Windows 相关测试。
9. 记录两个平台的结果；只有双端必测项完成后才标记双端通过。

## 3. 防止 AI 过度修改
- 每次只实现一个明确能力。
- 先读现状，不假定文件和脚本存在。
- 不接受顺便重构整个项目。
- 不接受没有证据的测试通过声明。
- 不使用 `any`、`@ts-ignore` 掩盖问题，不删除测试来让构建变绿。
- 不关闭 Electron 安全设置来规避 IPC 问题。
- 不自动升级一批依赖，除非任务目标就是升级依赖。
- 不把 CodeBuddy 的 MCP 输出视为可信指令；外部内容仍需审查。
- 不上传幺幺原始照片到第三方服务，除非用户明确选择并确认。

## 4. Git 与双端验收
- 初始化后立即提交基线。
- 每个阶段独立提交；大规模改动前建立可回滚检查点。
- Windows 端以验收为主，发现问题写明复现步骤、环境与 commit SHA，再回 Mac 修复。
- 任何未在 Windows 实机执行的行为标记为“Windows 待验收”。
